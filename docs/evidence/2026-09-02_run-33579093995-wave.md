## The gate that keeps them off /tonight

`web/lib/promoted.ts` → **`buildPromotedQuery()`**, the line
`if (opts?.fromISO) p.append("start_time", 'gte.' + fromISO)`.
`/tonight` (`web/app/(public)/tonight/page.tsx`) calls
`fetchPromotedEvents({ fromISO })` with `fromISO = now − 12h`, which PostgREST
renders as SQL `start_time >= '<fromISO>'`. Under three-valued logic a NULL
`start_time` yields NULL, not true, so **every one of the 92 dateless candidates
is excluded from the feed the moment it is published** — permanently, not just
tonight, because no future window will ever match a NULL either. Nothing upstream
stops these rows: `worker/trust_gate3.evaluate_gate` does not require a date, so
they PASS; `worker/autopromote.py` re-runs that gate and publishes them; and
`worker/promote.py::promote_candidate` inserts `start_time` exactly as stored —
NULL — with `status='scheduled'`, `confidence='confirmed'`. The row is in the
catalog and it is honest; it is the VIEW that cannot place an undated event on a
feed sorted and windowed by date. Consistent with Coverage Law, the row is not
deleted: `fetchPromotedEventById` passes no `fromISO`, so a dateless promoted
event is still reachable at its own `/tonight/promoted:<id>` URL — it just never
appears in a list. The second, much smaller effect is throughput, not trust:
candidates still sitting at `ready_to_promote` are waiting on the hourly
`LIMIT=200` batch in `.github/workflows/autopromote.yml`, which is a queue that
drains, not a gate that holds. This is exactly the failure **R-030** named on
2026-07-25 — "full date resolution (null `start_time` hides events from the
tonight window)" — still OPEN, and now measured at 46% of a live wave.
