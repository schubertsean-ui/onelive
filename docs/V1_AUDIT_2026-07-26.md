# OneLive — Deep Audit of Everything Built to Date (2026-07-26)

**Who this is for:** the founder. Plain language, no jargon without an
explanation, every number measured this session rather than quoted from an
earlier document. Where I could not verify something, it says so.

**What I was asked:** *"perform a deep, super deep evaluation of the overall code
built to date. I suspect it's bloated, has unnecessary content, contradictory
content, and is unfocused and has way too many rules to be useful."*

**How I checked:** ran the full gate (`bash tools/validate`), ran the whole test
suite in a clean environment, ran the session reconciler, read the GitHub Actions
history and job logs for every scheduled job, traced which code actually calls
which code, and measured the repository. Method notes are at the bottom.

## The verdict in six sentences

Your suspicion is correct, and it is worse and better than you think. **Better:**
the engineering underneath is genuinely strong — 1,665 passing tests, a real
trust architecture, careful credential handling, deterministic importers, and an
independent non-Claude reviewer that has caught real attacks. **Worse:** the
build has been optimising the *process of building* rather than the *product*, and
the two data pipelines that feed your website are **both broken right now** —
one because of a one-line workflow bug that has meant the local-venue feed has
**never once run on its schedule**, and one because the Anthropic account hit its
usage limit and will not work again until **2026-08-01**.

The single most important structural finding: **you told the agent on 2026-07-25
that you cannot hand-approve thousands of events. The decision was recorded, a
policy module was written, tests were written for it — and it was never connected
to anything.** The charter still says the opposite. So today a long-tail event
physically cannot reach your website without a human click, which is the exact
thing you said doesn't scale.

## 2. What is genuinely good (do not throw this away)

I want to be fair, because a lot of this is real and worth keeping.

1. **The trust architecture is sound and it is actually implemented**, not just
   described: provenance columns, a 4-state confidence model, row-level security
   on the database, a gate that decides promotion separately from the AI that
   extracts, `disputed` always shown. The separation is real in the code, not
   only in the docs.
2. **Credential handling is better than most production systems.** The database
   password is assembled inside a single step, URL-encoded, log-masked, never
   written to `GITHUB_ENV` or step outputs. Untrusted workflow inputs reach the
   shell only through environment variables, never string-interpolated. This is
   correct and I would not change it.
3. **The independent non-Claude reviewer earns its keep.** Reading the review
   history, the second-model seat caught a genuine fail-open bug (a `2>/dev/null`
   that conflated "file missing" with "write failed") that the first model had
   passed twice. That is the mechanism working exactly as intended.
4. **The deterministic importers are the right call.** Ticketmaster / SeatGeek /
   Eventbrite / venue ICS + schema.org feeds need no AI, cost nothing per event,
   and cannot hallucinate. This is your real data foundation and it is built.
5. **The test suite is not decorative.** 1,665 tests, green on a full-history
   clone, and the ones I read assert real behaviour including negative cases.
6. **`/tonight` is a real, working server-rendered feed** reading real rows, with
   an honest failure mode (it explains a misconfiguration rather than showing a
   blank page) and an additive union read so a secondary-source failure cannot
   blank a working feed.

## 3. Defects, ranked by what they cost you

### D1 — CRITICAL, FIXED IN THIS CHANGE: the local-venue feed has never run on its schedule

`.github/workflows/import_structured.yml` — the twice-daily deterministic import
of venue, university, library, civic and museum calendars — reads its fetch bound
as `${{ github.event.inputs.limit }}`.

On a **scheduled** run GitHub provides no `inputs` at all, so that expression is
the **empty string**. The workflow's own fail-closed guard then correctly refuses
to run. Result: it dies at the precondition step before fetching anything, every
single time.

Evidence: it has had exactly **one** scheduled run in its life — GitHub run
`30175059075`, 2026-07-25T21:09:09Z — and the log ends with
`LIMIT: limit input missing — the fetch bound is required — failing closed`.
Its four *successful* runs were all manual.

Why nothing caught it: no test exercised the scheduled path's variable
resolution, and in a code review the guard reads as a *virtue* — it looks like
exactly the fail-closed discipline the charter demands. `ingest.yml` and
`import_licensed.yml` both got the schedule-safe form right; this one file did
not.

**Fixed here:** the bound now pins the schedule side to a literal, in both places
it is read, and `tests/test_scheduled_inputs_contract.py` now scans **every**
scheduled workflow for the whole class of bug — proven to fail on the old form
and pass on the new one.

### D2 — CRITICAL, needs you: AI extraction is dead until 2026-08-01

Every scheduled ingestion run since 2026-07-25 ~21:00 fails with:

> `You have reached your specified API usage limits. You will regain access on
> 2026-08-01 at 00:00 UTC.`

(GitHub run `30186783965`, 2026-07-26T03:49:43Z; 10 of 10 sources errored, so the
run correctly refused to report success.) The spend cap did its job — the system
failed loudly and nothing false entered the database. But the long-tail
extraction path is offline for about six days.

This is a money decision, so it is yours: either raise the cap in the Anthropic
console, or accept that v1 launches on the deterministic feeds only. **My
recommendation is the second one** — see §7.

### D3 — CRITICAL: the founder's auto-publish decision was recorded and never wired

On 2026-07-25 you said, verbatim: *"Good lord I can't approve every one of
thousands of events!"* That was ratified and written up in
`docs/memory/decisions/2026-07-25_auto-publish-earned-confidence-ratification.md`,
with a clean policy table (anchor source → `confirmed`; two independent sources →
`likely`; one trustworthy source → published as `unverified` with a quiet marker;
conflicts and unreliable sources → human review).

`worker/publish_policy.py` implements that policy, purely and with exhaustive
tests. **Nothing imports it except its own test file.** The component that would
act on it, `worker/autopromote.py`, does not exist. The only code that promotes
anything is `api/ops_candidates.py` — the human ops screen.

So the decision is, in practice, not implemented. Worse, `CLAUDE.md` line 79
still reads *"Claude API — used only for weak-signal extraction … never to
auto-publish."* The charter contradicts a decision you ratified.

Note the honest part: the decision record set three conditions before the switch
flips, and **condition 1 is not met** — nothing updates source-reliability scores
from outcomes, so "graded unreliable" cannot gate anything yet. The wiring is
therefore real work, not a flag flip. It is the #1 item in `docs/V1.md`.

### D4 — HIGH: the highest-volume data source is manual-only

`import_licensed.yml` (Ticketmaster + SeatGeek — the bulk of the feed) runs
**only on manual dispatch**. Nine runs ever; the last was 2026-07-24T23:52Z. A
"what's on tonight" site whose main feed is refreshed by hand is not shipped.

The charter rightly forbids a scheduled job without a dead-man alarm, and that
alarm needs one healthchecks.io check plus one repository secret — a one-minute
task only you can do. It is ask #2 in `docs/V1.md`.

### D5 — HIGH: the armed cadence is fiction, and the documents assert it anyway

`ingest.yml` is armed at every 20 minutes. Measured over the last 45.1 hours of
history: **29 scheduled runs, mean interval 97 minutes — 21% of the armed
cadence.** GitHub's hosted scheduler simply does not deliver it. This is tracked
as R-023, but the register's own numbers are stale, and a contract test actively
*enforces* that the documents keep claiming 20 minutes. The harness is pinning
prose to an aspiration rather than to reality.

### D6 — HIGH: the one machine-verified fact in `STATE.md` is 14 days stale

`STATE.md` carries a `GROUND_TRUTH` block that the reconciler is supposed to
maintain, with a loud rule not to hand-edit it. Its contents:
`head: a0b3724`, `reconciled_at: 2026-07-12`, and PRs #4 and #7 listed as
**open** — you closed both on 2026-07-15.

The cause is structural, not sloppiness: `tools/session_reconcile.py` needs the
`gh` CLI and a database connection string, and the agent's sandbox has **neither**
(it exits 2 with "PR state UNVERIFIED", "DB facts UNVERIFIED"). So the one block
that is supposed to be verifiable truth is the least true thing in the file, and
"disk is truth" quietly degrades to "prose is truth." Meanwhile the prose grew to
**18,612 words** — a rollup nobody can hold in their head, in which 27 session
contracts are stacked newest-first with superseded claims left in place.

### D7 — MEDIUM (**corrected mid-audit**): the agent's own environment manufactures false red

**What I first wrote, and why it was wrong.** I recorded that master was red,
because `bash tools/validate` reported `pytest = FAIL` on
`tests/test_arming_smoke_binding.py`, which pins commit `bb92ff8`. I then did what
this project's own rule demands — *findings are claims until verified* — and
checked instead of asserting. The sandbox clone is **shallow** (50 commits).
`git fetch --unshallow` brings the commit into reach and **the test passes**
(`1 passed, 1 skipped`). The test's own docstring says exactly this: it fails
closed when the recorded commit is absent, and names the full-history CI job as
the authoritative venue. R-036 already said so too. **Master is not red. I was.**

**The real finding, which is sharper.** In the environment the agent actually
works in, `bash tools/validate` produces **three false failures** — `pytest`,
`surface_regression_exam` and `perf`, all from missing interpreter packages
(D12) — plus this fourth from the shallow clone. That is four red rows out of 19
that mean "your environment is incomplete," presented in the same column, in the
same red, as "your code is broken." Nothing in the harness distinguishes them.

That is corrosive in a specific way: it trains the reader — human or agent — to
scan past red. And the harness's own founding anti-pattern is that a failure must
never be indistinguishable from a non-event. Here the inverse holds, and it is
just as dangerous.

**The fix is not to loosen anything.** `tools/validate` should keep failing
closed and keep its non-zero exit, and additionally report `MISSING-TOOL` or
`UNPROVABLE-HERE` separately from `FAIL`, so a real regression is visible at a
glance. With a dev-dependency bootstrap and a full-history fetch, this tree is
**1,665 green**. Recorded as R-058, Step 3 of `docs/V1.md`.

### D10 — MEDIUM: 4,697 lines of off-mission product

The charter's "Current mission" is the live site behind the stealth gate. Also in

### D11 — MEDIUM: no verified deployment anywhere

I searched every tracked document for a deployment URL: **there is none.** No

### D12 — MEDIUM: the gate cannot tell a broken environment from broken code

`bash tools/validate` on a fresh clone reports `pytest = FAIL`,

bootstrap and no `requirements-dev.txt`. Failing closed is right; reporting a
missing tool as a *test failure* is not, because it trains everyone to read red
as noise. (With dependencies installed the tree is 1,664 pass / 1 fail; with
full history as well, 1,665 green — see D7.)

## 5. Where the weight actually is, and what to cut

I looked for what a reader must hold in their head *before writing a line of
code*. Today that is roughly **26,000 words** across `CLAUDE.md`, `STATE.md`,
`TODOS.md` and the five process documents — plus 36 red classes and 46 open
register rows. That is not a contract; it is a syllabus.

Three specific bloat mechanisms, each with a name:

1. **Prose ratchets.** Every review round appends a clause and deletes nothing.
   `CLAUDE.md`'s prime directive 1 is a **single 1,100-word sentence-chain** about
   one exception to one gate — an exception that is already enforced mechanically
   by `tools/classify_extraction_surface.py` and `tools/trust_gate.py`. **The
   prose is not the mechanism.** It can be one sentence plus a link.
2. **Narrative stored as state.** `STATE.md` interleaves 27 session contracts,
   premortem tag lists, and round-by-round review archaeology with the handful of
   facts a new session needs. The Construction Loop's `[S3:…]` tag blocks alone
   run to dozens of lines per contract.
3. **Meta-work that measures meta-work.** Brain IQ scores, reviewer scorecards,
   Kaizen trend meters, held-out brain evals, KPI registries. Each is defensible
   alone. Together they are a second product with no users.

**What I changed (this PR):**

- `CLAUDE.md` rewritten from 2,834 words to a short binding contract. Every
  invariant kept at full strength; the exception essay moved to
  `docs/EXTRACTION_EXCEPTION.md` where the mechanism it describes actually lives.
- One process document, `docs/HOW_WE_WORK.md`, replaces the working surface of
  five (`OPERATING_RULES.md`, `KAIZEN.md`, `skills/construction_loop.md`,
  `hats/README.md`, `skills/adversarial_review_v2.md`). The originals stay on disk
  as reference — tools and tests cite them — but they are no longer the thing you
  read to work.
- `docs/BAR.md` is new: **world-class defined once, per aspect, as a number, with
  the gate that enforces it and its honest current status.** This is the "front
  and centre" definition that was requested. `docs/WORLD_CLASS.md` remains the
  citation appendix behind it.
- `docs/INDEX.md` is new: every document classified **CANON** (binding),
  **REFERENCE** (read on demand), or **HISTORICAL** (never a rule). Only 9
  documents are CANON.
- `LIVE_READINESS.md` and `docs/SPRINT_LIVE_SITE.md` deleted — both are
  factually false now, and both are superseded by `docs/V1.md`. Git history keeps
  them.

**What I deliberately did NOT cut,** because cutting it would lose real quality:
no gate threshold, no test, no check in `tools/validate`, no invariant, and no
mechanical enforcement of any kind. Simplification here means *fewer words
governing the same mechanisms*, never *fewer mechanisms*. Loosening a gate is
your decision, not mine, and I am not asking for one.
