**Honest framing of the total:** ~10,000+ *places* exist in event-capable categories; after applying event-capability shares, **~4,000–5,000 will actually produce publishable events**. The 180-source catalog is therefore at ~4% of the addressable universe — the founder's instinct ("orders of magnitude short") is confirmed by the data.

**Scaling rule of thumb:** ≈ **140–170 event-producing sources per 100k population** (4,200 ÷ 3.0M), with a music-city multiplier: Austin skews high on music venues (250+ vs ~40–60 for a typical 1M-person metro) and wineries; a generic US metro projects at ~120–140/100k. Quick projections: Nashville metro (2.1M) ≈ 3,000–3,600; Denver (3.0M) ≈ 3,800–4,600; a 500k metro ≈ 600–800. Places-universe rule (pre-filter): ~330–400 event-capable-category POIs per 100k.

## (b) POI spine recommendation

| Option | Size | License | Verdict |
|---|---|---|---|
| **Overture Maps Places** | 53–61M global places ([Overture docs](https://docs.overturemaps.org/guides/places/), [AWS Open Data](https://registry.opendata.aws/overture/)) | **CDLA Permissive 2.0** — use, modify, monetize, share freely; attribution required ([Overture attribution page](https://docs.overturemaps.org/attribution/)) | **Primary spine** |
| Foursquare OS Places | 106M POIs (Dec 2025 release), 22 attributes, monthly refresh, Parquet on S3 ([FSQ announcement](https://foursquare.com/resources/blog/products/foursquare-open-source-places-a-new-foundational-dataset-for-the-geospatial-community/), [docs](https://docs.foursquare.com/data-products/docs/fsq-places-open-source)) | **Apache 2.0** — free commercial use | **Co-equal second spine** (it is a major *input* to Overture places; carries website/social attributes) |
| OpenStreetMap | crowd-mapped, patchy for businesses | **ODbL** — share-alike on derivative *databases* | **Enrichment only.** Honest note: mixing OSM rows into our source catalog could make the catalog an ODbL derivative database subject to share-alike. Keep OSM as a cross-check/geometry layer, not a merged catalog input, unless the founder decides publishing our source list openly is acceptable (it may even be on-brand — but that is a founder call, logged, not a default) |
| Google Places API | best freshness/coverage | **Prohibits storing/caching content beyond 30 days; only `place_id` storable indefinitely** ([Places policies](https://developers.google.com/maps/documentation/places/web-service/policies), [Maps service terms](https://cloud.google.com/archive/maps-platform/terms/maps-service-terms-20250501)); pay-per-call | **Rejected as spine** — a warehoused source catalog is the product of this engine; Google's ToS forbids exactly that. Permissible narrow use: a live lookup during human review of edge cases |
| SafeGraph / Placekey | commercial POI + free Placekey join-key API | commercial license / free tier | **Not needed at bootstrap.** Placekey optional later as a cross-dataset join key |

**Recommendation:** Overture Places as the canonical spine (CDLA-P 2.0 fits a truth-first platform: we can store, enrich, and keep provenance forever), inner-joined with FSQ OS Places (Apache 2.0) for website/social-handle attributes and as a confidence vote (a place present in both spines with matching name+geometry starts life more trusted — which maps directly onto the catalog's `credibility_weight`/`verification_anchor_score` fields). License obligations to carry in `docs/`: CDLA-P 2.0 + Apache 2.0 attribution notices; both permit commercial use with no share-alike. Expected spine size for the 14-county market: ~90–120k places, filtering to ~10k event-capable-category POIs.

## (c) Discovery pipeline — staged design

All stages write to a new `source_candidate` table (mirror of the trust pipeline's shape: every stage auditable, provenance on every row). **Trust invariant preserved: discovery auto-enrolls sources, never events.** An auto-enrolled source only ever produces *candidates* that still cross the existing gate; the AI-never-publishes physics is untouched. Per catalog schema, every enrolled row carries `allowed`/`explicitly_disallowed` and the prober obeys robots.txt — a `disallow`-ed calendar becomes `NEEDS_AGREEMENT`, never scraped.

| Stage | Input | Output | Size | Source-count gain (Austin) |
|---|---|---|---|---|
| **D0. Spine ingest** | Overture + FSQ Parquet (S3/DuckDB), market boundary polygon from `capcog.py` counties | ~90–120k place rows w/ category, name, geometry, website, social, dual-spine match flag | **S** (DuckDB reads Overture parquet directly; a weekend of work) | 0 sources yet — this is the substrate |
| **D1. Category filter + rank** | D0 rows + an `event_capable_categories.json` mapping (Overture/FSQ taxonomy → 1LIVE categories, the table in (a) as data) | ~10k event-capable POIs ranked by category prior × dual-spine confidence | **S** | 0 |
| **D2. Website resolution** | D1 POIs lacking a website attribute (~30–40%) | URL per POI via: FSQ website field → Overture `websites` → homepage search (one cheap search-API call) → TABC/SOS registry name match | **M** (search-API integration + name-match validation: fetched page must mention POI name/address — a triangulation rule the AI-extract path already uses) | 0 |
| **D3. Calendar-surface probe** (the heart) | POI + URL | Probe record: robots.txt; sitemap.xml URL patterns (`/events?`, `/calendar`, `/shows`, `/live-music`, date-slugged paths); fetch of homepage + top event-path candidates; detect (i) `schema.org/Event` JSON-LD (used by 100k–1M domains per [Google's registry](https://developers.google.com/search/docs/appearance/structured-data/event) — expect 15–25% hit rate on venue sites), (ii) ICS autodiscovery (`link rel`, `.ics` hrefs, webcal:), (iii) platform fingerprints (The Events Calendar, Localist, Squarespace/Wix events blocks, Dice/Eventbrite/Bandsintown/Songkick embeds or outlinks, Instagram/Facebook links), (iv) plain-HTML event lists | **M–L** (async fetcher + ~15 detectors; each detector is small, testable, and market-agnostic — Layer 1 code, written once) | 0 |
| **D4. Pathway classification + yield scoring** | Probe records | For each POI: `pathway_kind` ∈ existing kinds — `ics_feed` / `jsonld_embedded` / `calendar_platform` / `licensed_api` (via platform outlink, e.g. an Eventbrite organizer page) / `ai_extract_triangulated` (plain HTML) / `social` (IG-only) / `no_surface_yet` — plus `event_capability_score` (category prior × probe evidence) and `expected_yield` (events visible on probed page, recurrence hints) | **S** (deterministic rules over D3 output; extends `source_pathways.py`'s classifier — same PR rule: classifier and adapter move together) | classification of ~10k POIs; expect **~2,500–4,000 with a live surface** on first pass |
| **D5. Auto-enrollment** | Classified POIs above threshold | Catalog rows in `sources/markets/<id>` shard files, machine-generated with full provenance (`discovered_by: spine+probe`, spine IDs, probe timestamp, detector hits), status `NEEDS_BUILD`→`ADAPTER_BUILT` automatically for the structured kinds (they reuse `structured_feed.py` with zero new code); scores mapped onto existing `credibility_weight`/`verification_anchor_score` fields; dedupe against existing 180 first (below) | **M** (generator + import via `tools/import_sources.py`; human review queue ONLY for: ambiguous website match, robots-disallowed, `partner_agreement` candidates, and anything scoring in the gray band) | **+2,500–4,000 enrolled sources** |
| **D6. Standing loops** | Full POI set + enrolled catalog | (1) **Recheck cadence** for `no_surface_yet` POIs — venues add calendars: re-probe every 90 days, category-weighted (music venue 30d, dance studio 180d); a probe is ~5 HTTP requests, so re-probing 7k surface-less POIs quarterly is ~350k requests/quarter ≈ negligible. (2) **Dead-source detection**: per-source rolling stats (last-success fetch, last-event-seen, HTTP status history); 3 consecutive failed fetches or 120d event-silence in a category that should produce → status `DORMANT` (never delete — disputed/shown-never-hidden philosophy applied to sources: dormancy is recorded, provenance kept) with one automatic re-probe (site may have moved; sitemap re-resolve) before dormancy sticks. (3) **Spine refresh**: monthly FSQ + quarterly Overture releases diffed for new/closed POIs → new POIs enter at D1, closures flag their sources for dormancy review. (4) Dead-man ping on every loop (charter Sentinel rule). | **M** | steady-state +30–60 sources/month (new venues + calendar-adders) |

**Dedupe (against the existing 180 and within discovery):** three-key match — (1) normalized website domain (strip www/paths; the existing catalog's `base_url` makes this exact for most of the 180), (2) geo-proximity + name similarity (≤75m + Jaro-Winkler ≥0.88 on normalized name, the standard POI-conflation recipe), (3) spine ID once enrolled (Overture GERS ID / FSQ ID stored on every row, so future spine refreshes join exactly). Collisions merge provenance rather than dropping either record — the hand-curated row wins on identity, gains the spine IDs.

**Score → action bands:** auto-enroll ≥0.7; human queue 0.4–0.7 (target: <10% of volume — the review queue is sized for one person-hour/day); park <0.4 with recheck. Thresholds live in the market file as data; tightening is free, loosening is a gate-threshold question for the founder per the charter.

**Ratio math (events, which is what the founder's 50:1 bar is really about):** Ticketmaster's Discovery API carries "230K+ events" *globally* ([TM developer portal](https://developer.ticketmaster.com/products-and-docs/apis/discovery-api/v2/)); the US share and Austin's ~0.9% of US population put Ticketmaster's Austin inventory at roughly **1,200–1,800 listed events at any time, ~5,000–7,000/year** (build task: one Discovery API call with `dmaId` for Austin returns the exact `totalElements` — the repo already has a `ticketmaster.py` importer, so this number becomes measured, not estimated, on day one). The discovered catalog at ~4,000 producing sources × a conservative 3–6 events/month ≈ **150,000–290,000 local events/year → 25–55× Ticketmaster**; at the 6,500-source steady state with recurring series expanded, **50–100:1 is reached** — the founder's bar is attainable with this design, but only at the ≥4,000-source scale, which is the point of building the engine. (Calibration that the target is sane: Bandsintown operates at 65,000 venues / 2.3M events/year globally ≈ 35 events/venue/year — our per-source yield assumption is the same order. [CelebrityAccess](https://celebrityaccess.com/2025/10/22/bandsintown-hits-100m-registered-users-as-global-reach-tops-4-1b/).)

## Artist/group discovery (the non-venue half)

1. **Lineups are the primary artist mine — free with every extracted event.** Every gated event's performer strings become `artist_candidate` rows (same candidate→gate custody; an artist entity is *promoted* only when seen across ≥2 independent sources or matched to an authority record). 150k+ events/yr at 1–3 performers each bootstraps the local artist graph to thousands of entities within months at zero marginal crawl cost.
2. **MusicBrainz as the authority join** — open data (core data CC0), queryable by `area:Austin` for artists with begin-area/area in market cities; gives MBIDs, disambiguation, URLs/social links. (WS was proxy-blocked this session; the worker should query it directly, and a full-dump import is also viable.) Match lineup strings → MBID where possible; unmatched local acts remain first-class `unverified` entities — 1LIVE's whole thesis is that the long tail Ticketmaster ignores is the product.
3. **Artist surfaces close the loop:** each promoted artist's website/Bandcamp/IG (from MusicBrainz URL relations or the venue page itself) is probed by the SAME D3 prober — an artist's tour-dates page is just another source, enrolled with `pathway_kind` and provenance. Events discover artists; artists' pages discover events (including at venues not yet in the catalog — each unknown venue string becomes a D2-style resolution task). The graph feeds itself in both directions.
4. **Community groups:** library/city/parks program feeds (already flowing via `socrata.py` + the gov open-data pathway) name recurring organizers (chess club, run club, quilting guild) → group entities; plus the club-directory pages of running/cycling shops and breweries. Meetup's API is paid/restricted — treat as `partner_agreement`, not scrape.

## What the best do (precedent check)

- **Bandsintown** did NOT crawl venues first — it seeded **artist-side**: 2007 Facebook-app concert tracker importing users' music libraries/likes, artists self-managing tour dates, plus ticketing-partner feeds; 15,000 artists in under five years, now 700k artists / 65k venues / 2.3M events/yr ([Wikipedia](https://en.wikipedia.org/wiki/Bandsintown), [MBW](https://www.musicbusinessworldwide.com/live-music-discovery-platform-bandsintown-reaches-100m-registered-users/)). Lesson: the artist/producer self-serve loop (1LIVE's `manual_upload`/claim pathway) compounds — but it starts *after* coverage makes the platform worth claiming. Discovery-first, claim-second is the right order for 1LIVE.
- **Yelp/Google** bootstrapped listings from purchased/public business directories + web crawl + owner-claim flows — nobody hand-curated; the claim flow cleans what the crawl seeds. The now-open POI datasets (Overture/FSQ) are effectively that bootstrap, commoditized — 1LIVE gets for free what cost Yelp years.
- **Calendar-endpoint discovery at scale** has no single published playbook, but the components are proven: Web Data Commons shows schema.org adoption grew 3.1%→37.9% of crawled sites with JSON-LD dominant ([WDC](https://webdatacommons.org/structureddata/)), Google's registry pegs `schema.org/Event` at 100k–1M domains, and sitemap+path-pattern probing is standard crawler practice. The D3 prober is an assembly of known parts, not research risk.

## (e) Per-market replay recipe (what "add Nashville" looks like)

Because discovery lands as market data, replay is exactly the Layer-2 contract: **add files, never fork code.**

1. **Market file** (`sources/markets/nashville.json`): boundary reference (county set/polygon + resolver), timezone, locales, empty catalog shard. ~1 day incl. the boundary resolver data.
2. **D0–D1**: filter Overture+FSQ to the boundary; category mapping is global data, reused untouched. Compute: a DuckDB query over public Parquet — minutes, ~$0.
3. **D2–D4 probe pass**: for a 2M metro, ~7k event-capable POIs × ~5 fetches ≈ 35k HTTP requests + ~2–3k homepage-search calls. Wall-clock 1–2 days politely rate-limited; cost ≈ $30–80 search-API + cents of compute. AI is only in the loop for gray-band website disambiguation (cheap-tier per `docs/MODEL_ROUTING.md`) ≈ $20–50.
4. **D5 enrollment**: auto-enroll high-band (~1,800–2,800 sources for a 2M metro); human review queue ~200–400 rows ≈ 4–8 founder-or-delegate hours, phone-friendly.
5. **Localized seeds** (the only hand touch): the market's Ticketmaster/Eventbrite market IDs (existing `licensed_api` adapters, config-only), the city's Socrata/CKAN portal IDs, the 2–5 local-media calendars every city has, MusicBrainz area ID. ~1 day.
6. **Go-live order**: structured kinds (ICS/JSON-LD/platform) first — zero new code, high trust; `ai_extract_triangulated` sources ramp under the existing extraction-certification/gate regime and per-run budget ceilings unchanged (gates never relax per market — charter cost-discipline rule 3).

**Replay totals: ~1 week elapsed, <$200 direct cost, <1 day of human review, yielding ~2,000–3,000 enrolled sources per 2M-population metro** — versus the months the first 180 took by hand. National scale (top 50 metros) is therefore a ~year of background compute and review at ~$10k, not a re-engineering effort.

**Escalation flags for the founder (per charter):** (1) new external dependencies: DuckDB + spine Parquet ingestion, one search API — needs a STATE.md note and key-manifest entries; (2) OSM/ODbL decision above; (3) probe crawler egress volume may need a proxy/user-agent policy decision (identify honestly as 1LIVE bot — truth-first applies to our crawler too); (4) auto-enrollment thresholds are set conservative and only the *loosening* of them is founder-crucial.
