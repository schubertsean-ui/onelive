## 2. The practices that separate the top 0.1% — and 1Live's gap analysis

1Live baseline assumed: licensed APIs, ICS/JSON-LD/Localist parsers, AI extraction from HTML behind a trust gate, 4-state confidence (`unverified|likely|confirmed|disputed`), 3-way corroboration gating, county-boundary market model.

**1. Delete-rate as a first-class quality KPI.** PredictHQ's headline quality claim is destructive: up to 45% of ingested events deleted as inaccurate or spam, 30% spam/add-ons/duplicates, 10–30% duplicates per source ([data-quality](https://www.predicthq.com/intelligence/data-quality), [spam blog](https://www.predicthq.com/blog/detecting-and-eliminating-spam-events)). The elite operators measure and market what they *reject*.
- *1Live has:* the trust gate rejects, and disputed-shown-never-hidden is stronger than deletion for user trust.
- *Must add:* instrument the funnel — per-source rejection rate, per-source duplicate rate, per-gate-stage discard counts — as standing metrics (fits the Kaizen ledger). A source whose rejection rate spikes is a data incident, not noise. Publishing the delete-rate is also a differentiating marketing asset PredictHQ has proven.

**2. Entity spine before event stream.** PredictHQ's dedup/verification/ranking all run on a 55M-entity system (venues, performers, teams) — "integral to verification, enrichment, deduplication, and ranking" ([entities docs](https://docs.predicthq.com/getting-started/predicthq-data/entities)). Bandsintown's spine is artist identity wired into Spotify/Apple/YouTube. Events are ephemeral; entities are stable, so corroboration and dedup should key on (venue_id, performer_id, datetime), not fuzzy strings.
- *1Live has:* venues implicitly, via county-boundary markets and source parsing.
- *Must add:* a canonical venue table seeded from open data — Overture Places (~75M POIs, stable GERS IDs; [GERS](https://docs.overturemaps.org/gers/)) and/or Foursquare OS Places (100M+ POIs, open since Nov 2024), joinable via Placekey's free What@Where H3 identifier ([Placekey](https://www.placekey.io/how-it-works)). Every extracted event should resolve to a venue entity before it can reach `likely`; capacity/geo/timezone then come from the spine, not from re-extraction. A performer entity table (MusicBrainz-style IDs) is the phase-2 analog.

**3. Two-stage entity resolution, precision-first, with merge-don't-drop.** The proven pattern: cheap blocking/retrieval narrows millions of candidates, then an expensive classifier makes the final call — Foursquare's retrieval+rerank Place Match ([FSQ](https://foursquare.com/resources/blog/data/introducing-the-new-fsq-place-match-api/)), Yelp's Business Match tuned to F0.1=0.966, i.e. 99.1% precision at only 27.7% recall, because a wrong auto-merge is far costlier than a missed one ([Yelp](https://engineeringblog.yelp.com/2015/05/seeing-double-on-yelp.html)). And duplicates are *consolidated into one richer canonical record*, never just dropped — PredictHQ merges duplicates into one verified listing with corrected lat/long/timezone and confirmed or predicted end times ([enrichment](https://www.predicthq.com/intelligence/data-enrichment)); Google clusters duplicates and elects the most complete page as canonical ([canonicalization](https://developers.google.com/search/docs/crawling-indexing/canonicalization)).
- *1Live has:* 3-way corroboration is already a merge operation in spirit — multiple sources strengthen one event.
- *Must add:* an explicit blocking key (venue_id + date bucket) → pairwise classifier → canonical-event merge that keeps full per-source provenance (each merged source is corroboration evidence feeding the 4-state machine). Tune the auto-merge threshold precision-first like Yelp; below-threshold pairs go to the review queue, never auto-merge.

**4. Issue-queue automation with ranked-source arbitration and human escalation.** PredictHQ runs 100+ typed anomaly alerts; systems resolve most conflicts automatically using source depth and an *internal per-provider accuracy ranking*; only unresolvable conflicts reach the human data-assurance team ([blog](https://www.predicthq.com/blog/how-predicthq-identifies-and-fixes-event-issues-at-scale)). Yelp's equivalent is event-driven: every business create/change fires a match check via Kafka ([Yelp](https://engineeringblog.yelp.com/2015/05/seeing-double-on-yelp.html)).
- *1Live has:* admin review and the trust gate — but review as a stage, not a typed anomaly system.
- *Must add:* (a) a per-source historical-accuracy score (which source's start time won when sources disagreed?) used as the tiebreaker weight in corroboration; (b) typed issue classes (time conflict, venue mismatch, past-dated, suspicious recurrence, geocode outside county) each with an auto-fix path and an escalation path — so the admin queue receives only genuine ambiguity. This maps cleanly onto 1Live's Kaizen defect-class discipline.

**5. Become the write path: supplier-in-the-loop verification.** The strongest verification is making the supplier maintain their own record because it benefits them. Bandsintown: 700K artists correct auto-imported listings because those listings propagate to Spotify/Apple/YouTube/Google within 48h ([imported events](https://help.artists.bandsintown.com/en/articles/7048779-imported-events), [Billboard](https://www.billboard.com/pro/bandsintown-100-million-registered-fans/)). Google pays for its data with a 100% traffic-growth carrot ([Eventbrite case study](https://developers.google.com/search/case-studies/eventbrite-case-study)). Songkick's Tourbox, DICE/Luma/Posh dashboards — same move.
- *1Live has:* venue/creator claim actions (auth-protected) in the architecture.
- *Must add:* the incentive loop — a claimed venue's corrections feed corroboration as a high-weight source (never bypassing the gate: a venue claim is evidence, promotion still goes through the gate, preserving "AI never publishes" and no-pay-to-rank). Long-term carrot: 1Live pages emitting clean JSON-LD makes venues visible in Google Events, giving small venues a reason to keep their 1Live listing correct.

**6. Change-frequency-adaptive recrawl with a freshness SLA.** Google's crawl scheduler is the canonical design: crawl demand per URL scales with observed change rate, popularity, and staleness; ten unchanged visits demote the URL ([crawl budget](https://developers.google.com/crawling/docs/crawl-budget)). PredictHQ turns freshness into a product claim: API updated every minute ([event-api](https://www.predicthq.com/apis/event-api)).
- *1Live has:* scheduled ingestion (GitHub Actions cron) — currently fixed-cadence.
- *Must add:* per-source `last_changed` tracking with adaptive intervals (a venue calendar that changes daily gets crawled daily; one that changes monthly gets weekly), plus an event-proximity boost — recrawl frequency should rise as event start time approaches, since day-of cancellations/time-changes are the highest-stakes errors for a "tonight" product. This is also the budget-cap-friendly answer: adaptive scheduling spends crawl budget where change lives.

**7. Confidence/impact scoring as a separate, explainable layer.** PredictHQ's PHQ Rank (log-scaled 0–100) and Predicted Attendance are ML outputs built on entity features (venue capacity, performer history, season position) — a *ranking* layer cleanly separated from the *verification* layer ([PHQ Rank](https://www.predicthq.com/tools/rankings/phq-rank), [Predicted Attendance](https://docs.predicthq.com/getting-started/predicthq-data/predicted-attendance)).
- *1Live has:* the separation already — 4-state confidence is verification; feed ordering is display. This is architecturally ahead of most consumer apps.
- *Must add:* nothing structural; keep the invariant that ranking signals never mutate confidence state, and that no ranking input is purchasable (1Live's no-pay-to-rank is precisely the line Ticketmaster/aggregator ecosystems blur).

**8. Publish the bar you hold yourself to.** PredictHQ wrote and published QSPD — its own quality standard for event data — and a "forecast-grade data" buyer's guide, converting internal rigor into category definition ([QSPD](https://www.predicthq.com/intelligence/data-quality/standards), [forecast-grade](https://www.predicthq.com/blog/forecast-grade-data)). Yelp and Foursquare publish their matcher precision numbers ([Yelp](https://engineeringblog.yelp.com/2015/05/seeing-double-on-yelp.html), [Kaggle](https://www.kaggle.com/competitions/foursquare-location-matching)).
- *1Live has:* an unusually strong internal bar (trust invariants, golden-exam certification, The Record).
- *Must add:* a public-facing "how 1Live verifies events" page with real numbers (corroboration rates, dispute counts, correction latency). For a truth-first consumer brand this is the moat statement; PredictHQ proved the delete-rate itself markets.

**9. Treat platform APIs as revocable, and hedge with direct supply.** Eventbrite killed its public Event Search API in Feb 2020 ([GitHub](https://github.com/Automattic/eventbrite-api/issues/83)); Songkick stopped approving hobbyist keys ([developer](https://www.songkick.com/developer)); Ticketmaster caps at 5K calls/day with a 1,000-item paging wall ([docs](https://developer.ticketmaster.com/products-and-docs/apis/getting-started/)). The curated players (DICE/Fever, now merged; Luma; Posh) show the durable alternative: direct promoter/venue relationships where the partner's own dashboard is the source of truth ([DICE](https://dice.fm/partners), [merger](https://newsroom.feverup.com/en-US/250537-fever-and-dice-join-forces-to-build-a-live-entertainment-tech-powerhouse/)).
- *1Live has:* the right hedge already — first-party ICS/JSON-LD/Localist parsing against venue-owned surfaces (which venues won't revoke) plus AI extraction from HTML, with licensed APIs as supplements.
- *Must add:* per-source dependency tracking (what fraction of each county's confirmed events depends on a single revocable API?) as a standing dashboard number, and a venue-relations motion in the launch counties so the highest-value venues become direct, DICE-style, sources over time.

**10. Sub-venue and geocode discipline.** The open-geo world documents that cross-source POI placement disagreement (different geocoders, parking-lot centroids) is a dominant error class ([zephr.xyz](https://medium.com/@zephr.xyz/get-your-poi-out-of-my-parking-lot-addcd1dbad19)); Foursquare's matcher explicitly models sub-venues and chain variants ([FSQ](https://foursquare.com/resources/blog/data/introducing-the-new-fsq-place-match-api/)); PredictHQ "fixes and pinpoints location based on latitude, longitude and timezone tags" as a core dedup step ([intelligence](https://www.predicthq.com/intelligence)).
- *1Live has:* county-boundary assignment, which is robust to small geocode error at the market level.
- *Must add:* venue-level geocode reconciliation against the open spine (practice 2) and sub-venue modeling (Room B at a complex vs the main hall) — the failure mode that puts two "duplicate" events at one address when they are genuinely distinct.

## 3. Where 1Live's bar already exceeds the field

Worth stating for the founder: no benchmarked engine publishes a *user-facing* epistemic state machine. PredictHQ verifies for B2B forecasting but shows customers only the cleaned result; consumer apps (Bandsintown, DICE) show whatever the supplier entered. 1Live's 4-state confidence with disputed-shown-never-hidden, gate-custodied promotion, and no-pay-to-rank is a genuinely unoccupied position — the gap to close is industrial (entity spine, ER pipeline, adaptive recrawl, funnel metrics), not philosophical.
